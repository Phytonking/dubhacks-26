1. Summary

One business customer = one org = one agent = one Daytona sandbox. The sandbox hosts the agent brain (harness + tools + knowledge). Inside that agent, a voice capability lets the agent take and place phone calls through Photon's Spectrum Voice, using the same persona, knowledge, and contact memory as iMessage.

The main app (Next.js + MongoDB) is the control plane. A new business should go from signup to a live agent that answers texts and calls in under 5 minutes of owner time and under 60 seconds of wait time after clicking Deploy.

2. Goals / non-goals

Goals

  1. Self-serve: signup → describe product → Deploy → agent live on a real Photon line. No human on our side.
  2. One isolated Daytona sandbox per agent, identical baseline, disposable.
  3. Voice: inbound and outbound calls on the business's Photon iMessage line, answered by the same agent, transcripts in the same inbox next to texts.
  4. Mongo is system of record. Sandbox holds no durable state.
  5. Owner can watch live, take over, and kill.

Non-goals (v1)

  • Building our own telephony carrier. Photon supplies the line and SIP bridge.
  • Voice on WhatsApp (Photon voice supports iMessage lines only).
  • Multi-agent per business, custom-trained voice models, payments in call.

3. Key technical finding: voice is SIP, not app.messages

From Photon's Spectrum Voice docs:

  • Voice is SIP + RTP, not part of the spectrum-ts SDK. There is no voice.config() provider; calls do not appear in app.messages or app.webhook(). SDK call control and webhooks are "coming soon" with no dates.
  • Inbound: owner registers a per-line inbound route in the Photon dashboard with a SIP URI (sips: TLS port 5061, or sip: TCP 5060). Spectrum dials that URI. Our side must be a publicly reachable SIP endpoint with a trusted TLS cert (for sips:) and open RTP (UDP) port range. The URI user part is optional (sips:agent@host).
  • Outbound: our SIP client registers to sip.spectrum.photon.codes (TLS 5061, TCP 5060 fallback) with project ID as username and project secret as password. Spectrum places the call from the iMessage line.
  • No UDP signaling, no SRTP (audio is unencrypted RTP), WhatsApp numbers unsupported. Voice-only lines "coming soon". A free business profile (1–2 business days) is recommended before production outbound.
  • No mention of codecs, STT/TTS, concurrency, or duration limits. VERIFY with Photon.

Consequence: the Daytona sandbox cannot be the SIP endpoint itself. Sandboxes are per-tenant, ephemeral, auto-stop, and shouldn't hold Photon credentials or public SIP ports. We need a shared Voice Gateway outside the sandboxes that terminates SIP/RTP and bridges audio to the agent in the sandbox.

4.1 Where the "brain" runs for a call

Two modes; pick by spike measurements:

  1. Brain-in-sandbox (default). Gateway does STT and TTS. Per utterance, it sends text to the sandbox's Agent Runtime over an authenticated WebSocket and streams reply tokens back to TTS. Keeps one agent definition across text and voice, so memory, tools, and guardrails are shared.
  2. Fast-path brain in gateway. Gateway runs a small voice-tuned LLM loop itself with the agent's config + knowledge snapshot from Mongo, and calls into the sandbox only for tools. Use only if sandbox round-trip blows the latency budget.

Latency budget (inbound turn, end-of-speech → first audio): ≤ 1.2 s p50, ≤ 2.0 s p95. Requires a warm sandbox (see §8).

4.2 Call flow (inbound)

  1. Customer calls the business's iMessage-line number. Photon dials sips:<lineKey>@voice.<ourdomain>:5061.
  2. Gateway accepts, reads <lineKey> from the SIP URI user part → channel_lines lookup → orgId. Unknown key → reject.
  3. Gateway checks agents.status and enabledChannels.voice. If sandbox is stopped, wake it on INVITE (pre-warm during ringing) and play a short greeting from the gateway to cover the gap.
  4. Resolve contact by caller number (E.164), create calls doc, attach to the contact's single conversation. Load prior history for the agent's context.
  5. Loop: VAD → STT → agent turn (§4.1) → TTS. Barge-in cancels TTS and the in-flight turn.
  6. Each utterance is written as a messages row (channel:"voice", callId). Tool calls go to tool_calls.
  7. Hang-up or handoff: write calls.endedAt/durationSec/summary/outcome; summarizer extracts facts into contacts.facts with sourceMessageId.

Human takeover on voice: owner clicks "Take over" → gateway bridges the call to the owner's phone (outbound SIP leg via Photon) or ends with "someone will call you back" per org setting.

4.3 Call flow (outbound)

Agent tool place_call(contactId, goal) runs in the sandbox but executes through the Orchestrator → Gateway (the sandbox never holds Photon credentials). Gateway dials via sip.spectrum.photon.codes. Gated by consent flag on the contact, owner-enabled outboundVoice, quiet hours, and rate limit. Off by default (regulatory, see §11).

5. Daytona sandbox: the agent's home and its connection

One sentence: a Daytona sandbox is the agent's computer. We (the Orchestrator) own the key to that computer and can start, stop and delete it. The agent inside it holds no keys of ours: it holds one short-lived token, and it phones home to us over an outbound connection.
Verified 2026-10-17 (see TEST-REPORT-agent-runtime.html): on our current Daytona tier a sandbox has no general outbound internet (npm reachable; Modal and other hosts blocked). The dial-home Hub and sandbox-to-LLM-gateway paths below therefore need a Daytona tier with full egress. Until then the working path is: Orchestrator reaches agentd through the Daytona preview URL (port 8080), and the Modal call is made by our side between a /turn (prompt + tools in sandbox) and a /finalize (answer cleanup in sandbox) request. Modal credentials never enter the sandbox in either path.

5.2 The two connections

   CONTROL  (we reach the sandbox through Daytona's API)
   Orchestrator ──DAYTONA_API_KEY──► Daytona API ──► Sandbox  (create · start · stop · delete · run agentd)

   DATA  (the agent reaches us; outbound only)
   Sandbox: agentd ──wss + agent JWT──► Agent Hub (in Orchestrator) ◄── Channel Worker / Voice Gateway
                    └─ HTTPS + JWT ───► Agent API  ──► MongoDB
  • Control path (Daytona SDK, @daytona/sdk). Only the Orchestrator talks to Daytona. It authenticates with new Daytona({ apiKey, apiUrl, target }) and uses create / start / stop / delete / get / list, then sandbox.process.createSession() + executeSessionCommand({ runAsync: true }) to launch agentd as a long-lived process.
  • Data path (agent dials home). agentd opens one outbound WebSocket to the Agent Hub and keeps it open. The Channel Worker and Voice Gateway push turns to the agent down that socket and receive streamed replies back. The Agent API (HTTPS) serves config, knowledge search, message writes, tool-call audit, and facts.
  • Why not call into the sandbox through a Daytona preview URL? Preview links exist (getPreviewLink(port) returns a URL plus a token header; getSignedPreviewUrl embeds the token, default 60 s expiry), but they put a public HTTP surface on every tenant, require token juggling per request, and can't tell us whether the agent is alive. Dial-home gives us: no inbound exposure, presence = socket open, one auth model. Keep preview links only as a debug tool for operators.
  • Egress lockdown. Create sandboxes with networkBlockAll: false plus an allow-list (networkAllowList, comma-separated CIDRs; Daytona also has a domain allow-list) limited to the Hub, Agent API, and LLM gateway. Daytona's tier rules can override sandbox-level settings on lower org tiers, so confirm our org tier before relying on this VERIFY.

5.3 The baseline snapshot (built once, shared by every agent)

A Daytona snapshot is the pre-built image every sandbox starts from. We build one per release:

// scripts/build-snapshot.mts   (run in CI on every agent-runtime release)
import { Daytona } from "@daytona/sdk";
const daytona = new Daytona();

await daytona.snapshot.create({
  name: `agent-base-${VERSION}`,                 // e.g. agent-base-2026.10.17-1  (name = version)
  image: "node:22-bookworm-slim",                // must carry an explicit tag; :latest is rejected
  resources: { cpu: 2, memory: 4, disk: 10 },    // identical for every business at a given tier
});
// Layers on top of the base image (via a Dockerfile / declarative Image): bash + GNU utils,
// Hermes (or fx), agentd, voice session handler, tool runtime, pinned deps.
// Dockerfile route is CLI-documented:  daytona snapshot create NAME --dockerfile ./Dockerfile
  • Versioning: Daytona documents no version feature, so version lives in the snapshot name. agents.snapshotVersion and sandboxes.snapshotVersion record which one an agent runs.
  • Staleness: snapshots go inactive after 2 weeks unused and must be re-activated (daytona.snapshot.activate(name)). A daily job activates the current snapshot so Deploy never fails on it.
  • Warm pools: Daytona's docs mention warm pools for snapshots, where a create request "claims one warm sandbox from the pool instantly". Evaluate this before building our own pool (§9.1) VERIFY (configuration surface, per-org cost).

5.4 Initialize everything in one go

"One go" means one idempotent call: provisionAgent(orgId). The owner clicks Deploy (or the signup hook calls it early for a warm start); the Orchestrator does the rest. Creating the sandbox, starting the agent, getting it connected, and attaching its line are all steps of the same job, so they either all complete or the UI shows exactly which step to retry.

// orchestrator/provision-agent.ts
async function provisionAgent(orgId: ObjectId) {
  const agent = await agents.findOne({ orgId });                 // exactly one per org
  await step(agent, "claim_sandbox", async () => {
    // 1. Create (or claim from pool) the sandbox from the baseline snapshot.
    const sandbox = await daytona.create(
      {
        name: `agent-${orgId}`,                                  // idempotency: get() by name before create()
        snapshot: SNAPSHOT_NAME,                                 // agent-base-<version>
        language: "typescript",
        labels: { orgId: String(orgId), agentId: String(agent._id), snapshot: SNAPSHOT_NAME },
        envVars: {                                               // NOT secrets: everything here is readable by the agent
          ORG_ID: String(orgId),
          AGENT_ID: String(agent._id),
          HUB_URL: process.env.AGENT_HUB_URL!,                   // wss://hub.<ourdomain>/agent
          AGENT_API_URL: process.env.AGENT_API_URL!,
          AGENT_TOKEN: mintAgentJwt({ orgId, agentId: agent._id, ttl: "1h" }),
        },
        autoStopInterval: 15,                                    // MINUTES idle (SDK default 15; 0 disables)
        autoArchiveInterval: 7 * 24 * 60,                        // minutes
        networkAllowList: EGRESS_ALLOW_CIDRS,                    // Hub, Agent API, LLM gateway
      },
      { timeout: 90 },                                           // seconds
    );
    await sandboxes.insertOne({ orgId, daytonaId: sandbox.id, state: "creating",
                                snapshotVersion: SNAPSHOT_NAME, createdAt: new Date(),
                                lastActiveAt: null, costAccruedCents: 0 });
    await agents.updateOne({ _id: agent._id }, { $set: { sandboxId: sandbox.id } });
  });

  await step(agent, "start_agent", async () => {
    const sb = await daytona.get(`agent-${orgId}`);
    await sb.process.createSession("agentd");                    // long-lived process via a session
    await sb.process.executeSessionCommand("agentd",
      { command: "agentd start --config /workspace/config", runAsync: true });
    // agentd: fetch config + knowledge from Agent API, boot harness, dial the Hub, send "hello".
  });

  await step(agent, "await_hello", () => hub.waitForAgent(agent._id, { timeoutMs: 30_000 }));
  await step(agent, "health_check", () => hub.send(agent._id, { type: "ping-prompt" }));   // canned LLM turn
  await step(agent, "assign_line", () => lines.assign(orgId));                          // Photon pool (§9.1)
  await step(agent, "register_routing", () => router.refresh(orgId));
  await agents.updateOne({ _id: agent._id }, { $set: { status: "running" } });
}

step() writes {name, status, startedAt, error} to agents.deploy.steps[] and skips steps already marked done, which is what makes the whole job safely re-runnable and gives the UI its progress stepper.

5.6 Stop, wake, and token rotation

  • Stop. Daytona auto-stops after autoStopInterval idle minutes (default 15). Processes die with the sandbox, so agentd does not survive a stop. Hub sees the socket drop, agent state becomes sleeping.
  • Wake. On an inbound text or call, Worker/Gateway asks the Orchestrator to wake the agent: daytona.start(sandbox, 60), then re-run the start_agent step (create session + agentd start), then wait for hello. The message waits in the per-conversation queue; the Worker shows the typing indicator meanwhile. Whether Daytona can relaunch a process automatically on start is not documented VERIFY; if not, the Orchestrator does it as above.
  • Token rotation. JWT lasts 1 h; Hub pushes a fresh one down the socket before expiry. Revocation = Hub drops the socket and Agent API rejects that sandboxId.
  • Kill. daytona.delete(sandbox, 60, true); mark sandboxes.state="deleted"; disable lines.
  • Upgrade. New agents get the new snapshot name. Existing agents move on their next idle stop: delete, re-provision from the new snapshot (state is all in Mongo, so this is safe).

5.8 One-time platform setup (run once per environment)

Everything that must exist before the first customer can click Deploy. Scripted as pnpm platform:bootstrap so a fresh environment is one command:

  1. Create Daytona API key and set DAYTONA_API_KEY, DAYTONA_API_URL, DAYTONA_TARGET in the Orchestrator (not in Vercel's browser-exposed env, not in sandboxes).
  2. Build and activate the baseline snapshot (§5.3). Record its name in config.
  3. Stand up the Agent Hub, Agent API, Channel Worker and Voice Gateway on an always-on host with public TLS (wss://hub…, sips:…:5061).
  4. Generate the agent-JWT signing key; give Hub and Agent API the verifier.
  5. Seed the Photon line pool: each line gets a lineKey, an inbound SIP route in the Photon dashboard pointing at our Gateway, and a channel_lines row with status:"pool".
  6. (Optional) Pre-warm K sandboxes, or configure Daytona warm pools on the snapshot.
  7. Run the end-to-end smoke test: create a test org, provisionAgent, send a text, place a call, delete.

Per-customer onboarding is then only provisionAgent(orgId), with nothing manual.

const SANDBOX_ENV_KEYS = ["ORG_ID","AGENT_ID","SANDBOX_NAME","HUB_URL","AGENT_API_URL","LLM_BASE_URL","LLM_MODEL"] as const;

export function buildSandboxEnv(agent: Agent, platform: Record<string,string>) {
  const env: Record<string,string> = {};
  for (const k of SANDBOX_ENV_KEYS) env[k] = required(platform, k);   // missing key = fail the deploy
  env.AGENT_TOKEN   = mintAgentJwt({ orgId: agent.orgId, agentId: agent._id, ttl: "1h" });
  env.LLM_API_TOKEN = mintLlmToken({ orgId: agent.orgId, budget: agent.plan });
  assertNoPlatformSecrets(env);   // throws if any value equals PHOTON_API_KEY, DAYTONA_API_KEY, MONGODB_URI, ...
  return env;                      // passed as daytona.create({ envVars: env })
}
  • Allow-list, not block-list: new variables are not sent until someone adds them to the manifest.
  • Leak check: assertNoPlatformSecrets compares every outgoing value against the loaded platform secrets and aborts the deploy on a match. The smoke test also greps the sandbox env and process list for them.
  • Change after deploy: config changes (persona, model) go through GET /config on the Agent API, not env vars, so no restart is needed. Env changes only apply on the next provision or wake.
  • If we choose to send a raw secret anyway (for example the LLM key as a shortcut for the demo): Daytona's create() has a separate secrets parameter, but its semantics are not documented in what I read VERIFY. Treat anything in the sandbox as readable by the agent, and by anyone who can prompt-inject it.

5.10 LLM inference: Modal behind our LLM gateway

Inference runs on a Modal-hosted endpoint that speaks the OpenAI-compatible POST /v1/chat/completions API. Modal authenticates with one proxy token pair (ID.SECRET as a Bearer token), which is a single account-wide credential. So the sandbox must never call Modal directly:

Sandbox (harness) ──LLM_BASE_URL + LLM_API_TOKEN──► LLM gateway (ours, thin) ──Bearer MODAL_ID.MODAL_SECRET──► Modal endpoint
                                                       checks token · enforces per-org budget · logs usage → Mongo usage
  • LLM gateway is a small pass-through service (can live in the Orchestrator host). It validates LLM_API_TOKEN, maps it to an org, forwards the request body to MODAL_API_ENDPOINT/v1/chat/completions with the Modal credential, streams the response back, and records tokensIn/tokensOut into usage per org. It also lets us cap spend and cut one business off without touching the others.
  • Sandbox egress allow-list includes the LLM gateway, not Modal.
  • Request shape (from the Modal example): model, messages, temperature, max_tokens, top_p, stream, reasoning_effort. The harness (Hermes or fx) must be pointed at an OpenAI-compatible base URL; confirm each supports a custom base URL VERIFY.
  • Per-channel defaults: text stream:true, reasoning_effort medium or lower; voice stream:true, lowest reasoning setting and short max_tokens. The example's xhigh / max_tokens: 2048 would blow the 1.2 s voice turn budget (§4.1). Make these per-agent settings the gateway can clamp.
  • Reasoning output (if the model returns it) must be stripped before the reply is sent to a customer or spoken, and kept out of messages.body. Store it, if at all, on the tool_calls/turn audit record VERIFY response field names.
  • Cold starts: Modal endpoints can scale to zero. Measure first-token latency cold and warm in spike (b) and decide on a keep-warm setting for voice-enabled orgs.
  • Model naming: the endpoint URL says qwen-3-8 while the model id is Qwen/Qwen3.8-2.4T-A95B. Use the model id exactly as given; confirm with the endpoint owner that they match.

6. Message capture: every message in and out lands in MongoDB

Guarantee: every inbound and outbound message, on every channel, has a row in messages before the platform treats it as handled, and no message can reach a customer without passing through the one code path that writes that row. The agent in the sandbox is not trusted to do the recording; the platform does it around the agent.

6.1 Why this holds: one choke point per direction

  • The sandbox cannot send. It has no Photon credentials and no route to Photon (egress allow-list, §5.2). Its only way to speak to a customer is to return a reply over the Hub socket.
  • The Channel Worker (text) and Voice Gateway (calls) are the only components that talk to Photon. Both call a shared library, recordedIO, and nothing else touches Spectrum or SIP. Owner takeover replies from the web app also go through the Worker, so they are recorded the same way (sender:"owner").
  • Mongo, not the sandbox, is the record. If a sandbox dies mid-turn, the inbound message is already stored and the turn is retried.

6.2 Inbound: write first, then act

  1. Spectrum delivers an event (for await … of app.messages) or the Gateway receives a call utterance.
  2. Persist before anything else: upsert contact, upsert conversation, insertOne the message (direction:"in", deliveryStatus:"received"). The unique index on (channel, channelMsgId) makes Photon redeliveries idempotent: a duplicate-key error means "already stored, skip".
  3. Only after the insert succeeds does the Worker dispatch to the agent (or push to the owner if mode:"human"). If the insert fails, the Worker does not acknowledge or process the event, and retries with backoff.
  4. Unknown line, opted-out contact, or group message the agent ignores are still stored, with a handling field (agent | ignored | opted_out | rejected) saying what we did. Nothing is dropped silently.

VERIFY If Mongo is down, does Spectrum redeliver unacknowledged messages, or are they lost? Not stated in the docs we read. Mitigation regardless: a small local write-ahead spool (append-only file on the Worker host) takes the event first and drains to Mongo when it returns; the Worker's health check fails if the spool is non-empty for more than 60 s.

6.3 Outbound: record intent, send, confirm

  1. Intent row first. Before sending, recordedIO.send() inserts the message with deliveryStatus:"queued", a generated clientMsgId (unique, our idempotency key), the agentTurnId that produced it, and the guardrail verdict.
  2. Guardrail validators run (discount ceilings, hours, prohibited claims). A blocked reply is stored with deliveryStatus:"blocked" and a reason, then not sent. Blocked messages are visible to the owner.
  3. Set "sending", call Photon, then store the provider's id as channelMsgId and set "sent". Delivery receipts update to "delivered" or "failed" with deliveryError.
  4. Crash safety. A reconciler scans for rows stuck in queued/sending for more than 30 s. It checks for a provider id (when Photon exposes one for a send) and either marks sent, retries with the same clientMsgId, or marks failed for the owner to see. This gives at-least-once delivery with a record of every attempt; it cannot give exactly-once, since a crash between Photon accepting and our write is possible VERIFY whether Spectrum reply() returns a stable message id we can store.
  5. Long replies split into several bubbles produce one row per bubble, linked by replyGroupId.

6.4 Voice, tools, and the rest of the trail

  • Voice: each final STT utterance and each agent TTS reply is a messages row (channel:"voice", callId) written as the turn completes, not at hang-up, so a dropped call still leaves its transcript. The calls doc is created at INVITE and finalized at BYE; a reconciler closes calls left active after a Gateway crash.
  • Tool calls: the Agent API writes tool_calls for every call the agent makes (args, result, status, ms) before returning the result to the agent. A tool call with no audit row cannot happen because the tool runner lives behind the API.
  • Attachments: metadata and object-storage URL in the message; bytes never in Mongo (DB-DESIGN R7).
  • Reactions and edits: stored on the message (reactions[]), never overwrite the original body.

6.5 Mongo-side durability

  • Writes use writeConcern: { w: "majority", j: true } for messages, calls and tool_calls, so an acknowledged message survives a primary failover.
  • Atlas continuous backup with point-in-time restore on; retention window chosen with the privacy policy (DB-DESIGN R10).
  • messages is append-mostly: only deliveryStatus, deliveryError, reactions and handling are updated. Deletion happens only through the audited "delete contact" cascade. The Worker's Mongo user has no permission to delete or update other fields.
  • Every row carries orgId; recordedIO takes orgId from the authenticated line, never from the payload.

6.7 Schema changes this requires

The current messages validator (web/src/lib/schema.ts) does not allow this yet:

  • deliveryStatus enum is sent | delivered | failed. Extend to received | queued | sending | sent | delivered | failed | blocked.
  • channelMsgId is required, but a queued outbound message does not have one yet. Make it nullable, and change the unique index to a partial index (only where channelMsgId is a string). Add a unique index on clientMsgId.
  • Add: clientMsgId, agentTurnId, replyGroupId, handling, guardrail{verdict, reason}, attempts, callId.
  • Index (deliveryStatus, ts) for the stuck-send reconciler.
  • Dedicated Mongo roles: Worker/Gateway (insert + limited update on messages/calls/tool_calls), Web app (read, plus owner-send via the Worker), no component has drop/delete outside the cascade job.

7. Agent inside the sandbox

How the sandbox is created, connected and booted is in §5. This section covers what the agent does once it is running.

Per PRD.html §7, harness is Hermes behind an AgentRuntime interface (fx is the alternative); this PRD does not change that decision. The sandbox adds a voice session handler:

  • POST /session/:callId/turn (WebSocket preferred): input {utterance, partial?, channelCaps}, output stream of text-delta | tool-call | done | handoff.
  • Channel capabilities passed in context: for voice, short spoken-style replies, no markdown/URLs read aloud, spell numbers, confirm before irreversible actions.
  • Voice-specific tools: send_text_followup (iMessage the link/summary during or after the call), transfer_to_owner, end_call, schedule_callback.

Sandbox contents (baseline snapshot, versioned): runtime, harness, agent bootstrap, voice session handler. Mounted at start, not baked: persona, guardrails, knowledge (pulled from Mongo with the scoped token). Network egress: Orchestrator + LLM gateway + Mongo-facing API only (verify Daytona's egress controls).

Sandbox ↔ platform auth: sandbox boots with a short-lived JWT scoped to {orgId, agentId, sandboxId}. It calls a thin Agent API (hosted by Orchestrator or Next.js) rather than connecting to Mongo directly, so tenancy is enforced server-side and the DB password never enters the sandbox. Agent API endpoints: GET /config, GET /knowledge/search, POST /messages, POST /tool-calls, POST /facts, POST /heartbeat.

9. Connecting to the main app — onboarding in under 5 minutes

9.1 Principle: provision from pools, not on demand

Anything slow or manual is done ahead of time; Deploy only assigns and starts.

  • Warm sandbox pool: first try Daytona-native warm pools on the snapshot (§5.3); otherwise the Orchestrator keeps K pre-created sandboxes from the current snapshot, unassigned and stopped/idle. Deploy = claim one + inject org config. Fallback to cold create if pool empty.
  • Photon line pool (see §3.1: dedicated lines cost $250/month each, so a pool of them is real money; the shared-assignment alternative has no voice and customers must text first): Photon inbound voice routes are registered in the dashboard today [VERIFY: any API?], so lines are pre-provisioned and pre-routed. Each line's route points at our gateway with its own lineKey in the URI user part (sips:<lineKey>@voice.<domain>:5061). Deploy assigns a free line to the org (channel_lines.orgId, status:"active"). Zero Photon console work at onboarding time.
  • If Photon later offers line-provisioning and voice-route APIs, replace pool with on-demand; the interface stays LineProvider.assign(orgId).

9.3 Deploy transaction (idempotent state machine)

POST /api/agent/deploy → Orchestrator job, each step recorded on agents.deploy.steps[] so the UI stepper and retries are trivial:

  1. claim_sandbox — create (or claim a pooled) Daytona sandbox from the baseline snapshot with labels, env and scoped JWT; write sandboxes doc; set agents.sandboxId (§5.4).
  2. start_agent — launch agentd in a Daytona process session; it pulls config and knowledge from the Agent API.
  3. await_hello — wait for agentd to dial the Agent Hub (§5.2).
  4. health_check — canned prompt round-trip through the Hub.
  5. assign_line — claim a free channel_lines row from the pool (iMessage, plus voice route if enabled); status:"active".
  6. register_routing — Worker/Gateway pick up the new (line → orgId) mapping.
  7. smoke_test — optional test iMessage to the owner's phone; mark agent running.

Each step is idempotent and retried; failure leaves the agent in error with the failing step shown and a Retry button. Orphans (sandbox without agent, line without org) reaped by a nightly reconciler.

11. Security, privacy, compliance

  • Audio is unencrypted RTP between Photon and us (no SRTP). Document it; keep gateway in a trusted network path; revisit when Photon supports SRTP.
  • Photon project secret lives only in Orchestrator/Gateway/Worker. Never in sandbox.
  • Gateway rejects any INVITE not from Photon's source (IP allow-list VERIFY + SIP digest if available) and any unknown lineKey.
  • Per-org isolation: every Gateway/Agent API query takes orgId derived from the authenticated line or JWT, never from request body.
  • Guardrails (discount ceilings, prohibited claims, escalation triggers) enforced outside the LLM in the Agent API / gateway validators; applies to voice too.
  • Prompt injection by voice (caller says "ignore your instructions"): same tool allow-list and approval rules as text.
  • TCPA / call-recording consent / AI disclosure: inbound-first; outbound voice off by default; recording off by default; legal review before enabling. State-by-state two-party consent applies.
  • Retention and delete-contact cascade must include calls and recordings (DB-DESIGN R10).

12. Metrics

  • Onboarding: signup→live median (target < 5 min owner time; < 60 s Deploy), Deploy success rate (> 98%), step failure breakdown.
  • Voice: answer rate, turn latency p50/p95, barge-in correctness, dropped-call rate, calls/org/day, handoff rate, owner-rated call quality.
  • Cost per agent-day: sandbox seconds + tokens + STT/TTS + Photon line.
  • Reliability: sandbox cold-start p95, wake-on-INVITE gap heard by caller (target 0 s dead air).
