Voice Flow

Caller → Photon → ElevenLabs → our agent → ElevenLabs → caller, with the same business knowledge, memory and actions as text, and everything stored in Mongo.

1. Summary

ElevenLabs is now the voice layer: it takes the call from Photon over SIP, does speech-to-text, decides when the caller has finished talking, and turns replies into speech. It is not our agent. To keep one agent across text and voice, ElevenLabs should call our brain for every reply. ElevenLabs supports that: an agent can use a Custom LLM, a server that speaks the OpenAI chat-completions format and streams its answer.

Proposal. Build a small Voice Bridge service in agent/. Each time the caller finishes a sentence, ElevenLabs POSTs the conversation to the bridge. The bridge looks up the business and the caller, builds the same context our text agent uses (business rules, knowledge, the caller's profile and past texts), streams a reply from the model, runs tools, and streams the words back for ElevenLabs to speak. After the call, ElevenLabs sends a post-call webhook and the bridge saves the transcript, summary and facts to Mongo. The call shows up in the owner's inbox next to that customer's texts.

Why the change from the earlier voice PRD: that plan had Photon send calls to a SIP server we would run (LiveKit) and do speech-to-text and text-to-speech ourselves. You chose ElevenLabs for that part, which removes the hardest piece. What's left for us is the brain and the data, which is what this doc covers.

Status: the Photon side is configured (inbound calls to +1206…3267 go to sips:sip.rtc.elevenlabs.io:5061). Nothing in this doc is built or tested yet.

2. The call, step by step

  1. The caller dials the business's Photon number. Photon already routes inbound calls to ElevenLabs over SIP (done).
  2. ElevenLabs answers, plays a fixed first message (this is where we say it's an AI assistant), and the caller speaks.
  3. For each turn ElevenLabs transcribes the speech and sends the whole conversation so far to the Voice Bridge as a chat-completions request.
  4. The bridge works out which business (from the number dialled) and which customer (from the caller's number), loads memory, and streams a reply.
  5. ElevenLabs speaks the reply as it arrives. If the caller interrupts, ElevenLabs closes the stream and the bridge stops the model call.
  6. When the call ends, ElevenLabs posts the full transcript and analysis. The bridge stores them and updates the customer's profile.

3. Where the brain lives: two ways to wire it

A. Custom LLM (recommended)

ElevenLabs calls our bridge for every reply. One brain for text and voice: same persona, knowledge, guardrails, memory, tools. Owner edits in the console apply instantly to calls.

Cost: we are now in the latency path (§7), we must stream, and we need a public HTTPS endpoint.

B. ElevenLabs' own LLM + our tools

The agent's prompt and knowledge live in ElevenLabs. It calls our API through webhook tools only when it needs data or an action.

Cost: two brains that drift apart (prompt copied into ElevenLabs), guardrails only by prompt, memory only if the model chooses to call a tool. Benefit: least latency risk, least code.

Safety net: start with B for a 30-minute smoke test (proves the phone path works end to end with ElevenLabs' stock agent), then switch the same agent to A. If A cannot hit the latency target after tuning, B with a richer set of tools is the fallback. The decision uses measured numbers (§7).

4. The Voice Bridge

A small HTTP service in agent/ (new file voice-bridge.ts), always on, reachable on public HTTPS. For the hackathon, run it locally behind a tunnel (e.g. Cloudflare Tunnel or ngrok); later deploy it to an always-on host. Two endpoints:

EndpointCalled byDoes
POST /voice/llm/chat/completionsElevenLabs, once per caller turnIdentify, build context, stream the reply, run tools
POST /voice/webhooks/elevenlabsElevenLabs, once after each callVerify signature, finalize the call record, import transcript, extract facts

Per-turn logic

  1. Authenticate the request (shared secret; see §9).
  2. Identify the call. ElevenLabs gives agents system__caller_id, system__called_number and system__conversation_id as dynamic variables. We put them into the agent's system prompt on one machine-readable line, e.g. [call caller={{system__caller_id}} called={{system__called_number}} conv={{system__conversation_id}}]. The bridge reads that line from the incoming system message and strips it before the model sees it.
  3. Resolve business (channel_lines by the called number), customer (contact by the caller's E.164 number, any channel), conversation (the one per contact) and call record (calls, created on the first turn, keyed by the ElevenLabs conversation id).
  4. Build context with the same builder as text (context.ts): business rules, voice style, top knowledge matches, the caller's profile and facts, conversation summary, the last texts and calls, then the live call transcript from the request. Mongo reads run in parallel.
  5. Stream the model. Tool loop on the host (up to 3 rounds; see §6). If a tool is slow, send a short filler first ("One moment... "), as ElevenLabs recommends.
  6. Guardrails on the stream. Hold text until a sentence is complete, check it (discount cap, forbidden claims), then release it. A violating sentence is replaced by a safe line. This is how our existing text guardrail works, applied per sentence instead of per message.
  7. Persist. Save the caller's turn immediately; save the agent's turn when its stream completes (flag it interrupted if the caller cut in).

Interruptions

When the caller talks over the agent, ElevenLabs drops the connection. The bridge must cancel the model request right away (no wasted tokens, no stale text) and only store what could have been spoken.

5. Data and memory

  • Same customer across channels. A caller who texted last week is recognized by phone number. Contact lookup for voice searches handles across all channels, then adds a voice handle if missing. (Current unique index is per channel, so the lookup is a query change, not a schema change.)
  • One conversation per contact (existing rule). Call turns are messages with channel:"voice" and a callId, so the inbox shows texts and calls in one timeline.
  • calls collection (exists, empty): add provider:"elevenlabs", providerConversationId (unique), analysis, costCents, terminationReason.
  • Message ids for dedupe: channelMsgId = "el:{conversationId}:{turnIndex}", so retries and the post-call import never create duplicates (existing unique index on channel + id).
  • Post-call import is authoritative. Live rows can be incomplete (interruptions). When the webhook arrives, the bridge reconciles by turn index against ElevenLabs' transcript.
  • After the call: store ElevenLabs' summary on the call and in the conversation summary; run fact extraction (name, needs, budget) into contacts.facts with a pointer to the source message; update stage if clear; add a usage record (voice seconds, tokens).
  • Recordings: do not store audio by default (consent rules differ by state; see §9). Store transcripts only.

System tools (end_call, transfer_to_number, skip_turn, language_detection, voicemail_detection) are sent to a Custom LLM in the standard OpenAI tools parameter, and the model's tool calls come back in OpenAI format. Our own tools run inside the bridge and are never exposed to ElevenLabs.

7. Latency

Voice feels broken above about 1.5 s of silence. Target: first audio within 1.5 s of the caller finishing, median; under 2.5 s at p95. (Earlier PRD target was 1.2 s median, which may be too tight with a third-party voice layer; confirm by ear.)

StageEstimateSource
End-of-turn detection and speech-to-text~300–500 msestimate ElevenLabs-owned
Network ElevenLabs → bridge~50–100 msestimate
Context load (Mongo, parallel)~30–80 msestimate Atlas round trip
Model: time to first sentence~400–700 msMeasured: whole 56-token reply from Modal took 473 ms (non-streaming); first-token time while streaming not yet measured
Text-to-speech start~150–300 msestimate ElevenLabs-owned
Total~1.0–1.7 sNeeds a real call to confirm

Where we save time

  • Skip the sandbox on the hot path. The text path does sandbox /turn → model → sandbox /finalize, which measured about 880 ms for a voice-style turn. The bridge builds the prompt itself and calls the model directly, saving roughly the two sandbox round trips. Tools that truly need the sandbox (later) are called only when needed.
  • Stream tokens and release at sentence boundaries; ElevenLabs can start speaking before the reply is finished.
  • Short replies: 1–2 sentences, numbers spelled out (existing voice style rule).
  • Keep the bridge warm and near Atlas and Modal (region choice when we deploy).
  • Prompt-cache the stable prefix (business rules + knowledge) if the provider supports it.
Unknown that can break the plan: our model gateway currently calls Modal with stream:false. Whether the Modal endpoint streams, and its first-token time, decides whether Option A is viable. This is the first thing to measure (V1).

9. Security and compliance

  • Bridge auth. Use a long random secret. ElevenLabs' Custom LLM page says to store an API-key secret in their settings but does not state which header it is sent in; verify with a test request, and also put an unguessable token in the URL path as a second factor. Reject everything else.
  • Webhook auth. Verify the ElevenLabs-Signature header against the raw body with their SDK's constructEvent. Their docs don't state the tolerance window; reject stale timestamps anyway. Optionally allow-list their published egress IPs.
  • Business and caller come from the call, not from claims. The called number maps to the business through channel_lines; speech cannot change it.
  • Secrets stay out of prompts. Don't put keys in dynamic variables that reach the model; ElevenLabs offers secret__ variables restricted to headers.
  • Disclosure and recording. Say up front that this is an AI assistant. Don't record audio by default. Some US states require all-party consent for recording; get legal input before enabling recordings or outbound calling.
  • SIP inbound auth. ElevenLabs recommends digest authentication over IP allow-lists because carrier IPs vary. Photon supports sending SIP credentials; we currently send none. Worth adding once a first call works.
  • PII. Transcripts are personal data; same retention and delete-contact path as messages (open item R10 in the database review).
