Sales Agent Control Plane

A Next.js dashboard where a business owner configures, deploys, and supervises AI sales agents that talk to customers by text and voice, for any product the owner describes.

1. Summary

Model: one business customer = one org = one agent = one Daytona sandbox. Business owner signs in, describes their product (or uploads a catalog / docs / FAQ), and clicks Deploy. We provision the sandbox, start the harness, and attach a Photon iMessage line for that business. Channel rollout is staged: iMessage first and done well, then WhatsApp (Photon's WhatsApp Business provider), then SMS and voice later. The data model and worker are channel-agnostic from day one so each new channel is an adapter, not a rewrite. All data (business profile, knowledge, contacts, every text and call, transcripts, leads, tool calls, usage) is written to MongoDB as the system of record. The owner reads and acts on all of it in the Next.js app: watch conversations and calls live, review leads, take over any thread.

Stack decisions already made: MongoDB for all persistence · Next.js for the owner app · Photon (Spectrum) for channels · Daytona for one sandbox per agent. Open: harness (fx vs Hermes) — recommendation in §7.

2. Goals / non-goals

Goals (MVP)

  • Product-agnostic: agent behavior comes from owner-supplied config + knowledge, not code.
  • Exactly one agent per business customer, one Daytona sandbox, fair and isolated.
  • MVP: iMessage only, polished (typing indicators, threads, reactions, groups, attachments, dedupe, ordering). Next: WhatsApp. Later: SMS, voice. All via Photon; same persona, knowledge, and contact memory across channels.
  • MongoDB is the system of record for everything: all businesses, all contacts, all conversations, calls, transcripts, leads, audit.
  • Owner sees only their own data in the Next.js app: live inbox (text + calls), human takeover, lead capture.
  • Full audit log of every tool call the agent makes.

Non-goals (MVP)

  • Payments / checkout inside chat.
  • Multi-seat teams, RBAC beyond owner/admin.
  • Custom-trained models.
  • Building our own channel gateway (Photon does that).
  • SMS and voice in the MVP (designed for, built later). WhatsApp is the first expansion, not MVP.
  • Mobile app for the owner.

4. Architecture

Call flow (inbound voice) — LATER PHASE, not in MVP

  1. Customer calls the business's Photon line (SIP) → call audio reaches the Channel worker via the Spectrum voice provider.
  2. Worker creates a calls doc, resolves the same contactId used for texts, and loads that contact's prior history.
  3. Speech-to-text turns audio into utterances; each utterance goes to the same harness session; reply text goes to text-to-speech and back on the call. (Who supplies STT/TTS — Photon or us — is an open question, §12.)
  4. Each utterance is stored as a messages row (channel:"voice", callId); call summary, duration, and outcome written when the call ends.

Message flow (inbound text: iMessage in MVP; WhatsApp follows the same path)

  1. Customer texts the agent's Photon line → Photon Cloud streams it to the Channel worker over the Spectrum connection (app.messages).
  2. Worker resolves (line, sender) → orgId (the business's single agent) + contactId + conversationId in MongoDB; stores the inbound message with its channel (imessage now; whatsapp next).
  3. If conversation is in human mode → push to owner via SSE, stop. Otherwise forward to the agent's sandbox harness session.
  4. Harness runs the loop (LLM + tools inside sandbox); streams parts back.
  5. Worker applies guardrails, sends via message.reply() inside space.responding() (typing indicator), stores the outbound message + tool-call audit rows.
  6. Dashboard updates via change streams → SSE.
Why a separate Channel worker: Spectrum consumes a persistent stream (for await … of app.messages). That does not fit Vercel serverless functions. Host the worker on any always-on runtime (Fly/Railway/a small Daytona sandbox of our own). Photon also documents a Webhooks mode with Hono/Express/Elysia adapters; if it fits our scale, the worker could be replaced by a Next.js route handler. Spike this first.

5. Photon

Photon's product for us is Spectrum (spectrum-ts, MIT, TypeScript): one agent codebase, many channels. Spectrum Cloud is the hosted path (signup at app.photon.codes → project ID + secret). Self-host options exist (@spectrum-ts/imessage-local, own gRPC endpoints) but local iMessage is Mac-bound and not production-scalable.

Pricing, rate limits, multi-tenant model (project per customer vs one project many lines), attachmentsUnknown — not in public pages we read. Ask Photon (dashboard or ryan@photon.codes).
Staged channels: iMessage → WhatsApp → SMS/voice. Spectrum is built so the same app.messages loop serves every provider; adding a channel is adding a provider entry (e.g. @spectrum-ts/whatsapp-business) plus a thin adapter on our side. We normalize everything into one contact → conversation → message model in Mongo, tagged with channel, so the owner app and harness never branch on channel except for capability differences.

Channel adapter (what makes WhatsApp cheap to add)

interface ChannelAdapter {
  channel: "imessage" | "whatsapp" | "sms" | "voice";
  capabilities: { typing: boolean; reactions: boolean; threads: boolean;
                  groups: boolean; attachments: boolean;
                  freeformWindow?: "unlimited" | "24h"; requiresTemplates?: boolean };
  normalizeInbound(space, message): InboundMessage;   // -> our model
  send(space, out: OutboundMessage): Promise<SentReceipt>;
}

The worker holds a registry of adapters keyed by channel. The harness is told the active channel's capabilities in its context (e.g. keep replies short, no markdown on iMessage).

Phase 1 definition of "iMessage mastered"

  • Reliable inbound/outbound on a dedicated Photon iMessage line, per business, with dedupe on channelMsgId and in-order handling per conversation (queue per conversation, one in-flight agent turn).
  • Typing indicator while the agent works (space.responding), natural reply pacing, long replies split into message-sized chunks.
  • Threaded replies, reactions (read and send), attachments in and out, group chats handled explicitly (reply only when addressed, or off by default).
  • Delivery/failure handling and retry; an owner-visible failed-send state.
  • Human takeover: while mode=human, the agent stays silent and owner replies go out through the same line.
  • Opt-out ("stop") handled automatically; first-contact greeting and business hours behavior.
  • Everything persisted to Mongo; owner can see it live in the inbox.

WhatsApp (next) — what changes

  • Provider: Photon's whatsapp-business (WhatsApp Business Platform). Expect Meta business verification per business and a registered number; owner onboarding gains a "connect WhatsApp" step.
  • WhatsApp restricts free-form messages outside a customer-service window and requires approved templates for business-initiated messages. These are Meta rules as I understand them; confirm exact limits through Photon's provider docs. The adapter's freeformWindow / requiresTemplates capabilities and a templates collection cover this.
  • No Mongo schema change beyond new channel value, line capabilities, and templates. Same contact can have both an iMessage and WhatsApp handle.

Connection sketch

import { Spectrum } from "spectrum-ts";
import { imessage } from "spectrum-ts/providers/imessage";

const app = await Spectrum({
  projectId: process.env.PROJECT_ID,
  projectSecret: process.env.PROJECT_SECRET,
  providers: [imessage.config()],
});

for await (const [space, message] of app.messages) {
  await space.responding(async () => {
    const agent = await router.resolve(space, message);     // Mongo lookup
    const reply = await agent.handle(message);              // sandbox harness
    await message.reply(reply);
  });
}

Example above is adapted from the Spectrum README; router and agent are ours.

Avoid: Photon's older imessage-kit (reads macOS chat.db, sends via AppleScript, polls every 2s, no typing indicators, tied to one Mac). Fine for demos, wrong for a product.

Recommendation: start with Hermes, behind our own AgentRuntime interface.
  • Sales agents are conversational, long-lived, and benefit from persistent memory + skills (learn objections, product facts). fx is a coding agent; most of its tool surface is irrelevant to selling.
  • Daytona is first-class in Hermes; with fx we'd write and maintain the adapter.
  • Both lack a Photon bridge, so that cost is equal.
Pick fx instead if: you want a pure-TypeScript stack, tight AI SDK / AI Gateway integration, and agents whose job is mostly running code in the sandbox rather than conversation.
Before committing, 1-day spike for each: (1) Hermes: how do we feed it a message and get a reply programmatically (API server / ACP / CLI one-shot)? Per-agent isolation via profiles or one install per sandbox? (2) fx: does a custom Daytona SandboxSession take under a day? (3) Latency of first reply from a stopped sandbox. Decide with measured numbers.

8. MongoDB data model

Everything is stored in MongoDB Atlas: business customers, agent config, knowledge, contacts, every message and call across iMessage/SMS/voice, transcripts, leads, tool-call audit, sandbox state, usage. The only things outside Mongo are transient (sandbox disk, call audio in flight) and optionally call recordings in object storage referenced by URL from Mongo. Harness-side memory is treated as a cache: durable facts the agent learns about a contact or product are written back to Mongo. Every doc carries orgId; every query is scoped by it (one DB, shared collections, tenant-scoped).

10. Security & safety

  • Sandbox = untrusted. No platform secrets inside; scoped, short-lived tokens only.
  • Guardrails enforced outside the LLM (worker-side validators on discounts, hours, prohibited claims), not just in the prompt.
  • Prompt injection from customer messages assumed. Tools that mutate state (refund, discount, send email) need allow-lists and, where configured, owner approval.
  • Per-org data isolation in every Mongo query; test cross-tenant access explicitly.
  • Compliance: SMS/iMessage/voice outreach is regulated (TCPA, opt-out handling, call recording consent). Inbound-first in MVP; STOP/opt-out honored automatically; outbound campaigns gated until reviewed. This needs real legal input.
  • Full audit trail in tool_calls; kill switch per agent and per org.
