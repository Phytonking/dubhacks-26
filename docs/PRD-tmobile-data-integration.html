1. Summary

T-Mobile is our example client. The sandbox gives us a catalog, 5,000 households and 50 ready-made personas, but no names, phone numbers, or message text. Our agent today only has keyword search over owner-written knowledge rows; it has no customer record in its prompt and no live tools.

This PRD defines how the T-Mobile data gets into MongoDB Atlas and the agent, split by how fast the data changes:

  • Slow / policy data (plans, promos, rules) is backfilled into knowledge as chunks.
  • Customer data is linked to a contact by account id and snapshotted with a timestamp; the live API stays the source of truth.
  • Personality and memory are Atlas-owned: a character profile per contact, a rolling summary, learned facts and open commitments that persist across channels and sandbox restarts.
  • Actions (price a cart, check eligibility) go through audited agent tools that call the sandbox API.
Principle. The sandbox API owns facts about the account. Atlas owns the relationship: who this person is to us, what we said, what we promised. Never let the agent state a price or eligibility from memory; it must come from a tool result or knowledge chunk from this turn or a snapshot with an age.

2. Goals / non-goals

Goals

  1. An agent texting as T-Mobile answers plan, promo, trade-in and upgrade questions correctly from real sandbox rules, with zero invented numbers.
  2. Each of the 50 personas is a recognisable person (name, household, tone, history) the agent greets and remembers, not a row of fields.
  3. Anything learned or promised in a conversation survives restarts, sandbox sleep and channel changes (iMessage today, WhatsApp/SMS/voice later).
  4. Integration is a seed + adapter, not agent code: a second client (e.g. the Sunrise Bike Shop demo) must work with zero code changes (PRD.html phase 3 goal).
  5. Every external call is in tool_calls; every claim is traceable to a chunk, snapshot or tool result.

Non-goals

  • Mirroring all 5,000 accounts, 126k usage rows or 53k bills into Atlas.
  • Real charges. Checkout in the sandbox is mock and in-memory.
  • Scoring the churn labels. They are held out by the organizers and not in the repo.
  • Customer-facing PII storage beyond the demo set.

7. Path B: customer linking + snapshots

7.1 Identity bridge

The dataset has no handles. We create the bridge:

  1. Seed creates one contact per persona (50) with a demo handle (Photon test number or a placeholder E.164 under +1555… for non-live demos) and externalRefs=[{tmobile, ACC-PERSONA-nn}].
  2. Inbound message: (orgId, channel, address) → contact → externalRefs → account id. Already unique-indexed, no router change.
  3. Unknown handle: contact is stage:new with no externalRefs. Agent treats them as a prospect and may ask for lines, budget, usage (the matchmaker flow). It never guesses an account. Linking to a real account later is an owner action, logged.
  4. Prospects (PROSPECT-nn) get externalRefs.kind="prospect" and their stated_* fields as facts. No context call exists for them.

7.2 Snapshots

  • At turn start, if the contact has an account ref and the newest snapshot is older than the TTL (default 24h) or the sandbox as_of changed, call /context and insert a snapshot. Fall back to the last snapshot if the API is down, and tell the agent its age.
  • The prompt gets a compact digest, not the raw JSON (about 300 tokens): plan, lines with device age and payoff status, eligible lines, latest bill and change reason, support 90d count, risk signals.
  • Diff against the previous snapshot on refresh (bill rose, installment ended, new support contact). Diffs become events the agent can mention naturally and feed §9.

8. Persona layer: making it feel like a person

Two layers, both stored in Atlas, both generated once and then frozen so the same person is the same person every demo.

8.1 Agent voice (per org, set once)

orgs.brandVoice + agents.persona for T-Mobile: direct, friendly, plain language, no jargon, never pushy, always says what it costs per month and today. Includes do/don't examples. This is the "personified" assistant.

8.2 Customer character sheet (per contact)

Dataset fields are mapped deterministically; invented flavour is generated once with a fixed seed from the persona id, marked synthetic:true, and never contradicts the dataset.

The prompt composes org voice → character sheet → snapshot digest → memory → relevant knowledge in that order, so identity and hard constraints sit before retrieved text.

Honesty rule. Personification changes how the agent talks, not what is true. Backstory and "knowing" the customer must come from the dataset; invented colour is never presented as a fact about the real account. The agent never claims to be a human; the disclosure text from agents.disclosure goes in the first message of a new conversation.

9. Memory: how it stays

Four layers, each with an owner and a write rule. All in Atlas, loaded by the host at turn start (the sandbox may sleep; nothing is stored only there).

LayerFieldWritten byLifetime
Account statecustomer_snapshotsHost, from APILast 5 versions
Learned factscontacts.facts[] (exists: text, sourceMessageId, learnedAt)Agent via memory.remember, host validatesUntil contradicted or owner deletes. Add confidence, supersededBy
Conversation summarycontacts.memory.summary, summaryUpToMsgIdHost, after every N messages or idle gapRolling. Recent 12 messages stay verbatim, older ones fold into the summary
Open loopscontacts.memory.openLoops[{text, dueAt, status, sourceMessageId}]Agent via memory.commitUntil done. Surfaced first next turn ("you asked me to check the trade-in value on your iPhone 13")

Rules

  • Facts vs dataset. Facts store what the customer said ("moving in January", "daughter needs a phone by her birthday"). They never duplicate dataset values; those come from the snapshot so they cannot go stale.
  • Provenance. Every fact and open loop links a sourceMessageId. Facts with no source are rejected by the host.
  • Contradiction. A new fact that conflicts marks the old one supersededBy; nothing is hard-deleted so the inbox can show history.
  • Cross-channel. Memory hangs off the contact, not the handle, so iMessage → WhatsApp → voice shares it (already the conversation model: one per contact).
  • Owner control. Inbox contact panel shows profile, facts, open loops, snapshot age and a "forget" button. Edits are audited.
  • Reset for demos. seed-tmobile.mts --reset-personas restores profiles/memory to the seeded state without touching knowledge.

11. Guardrails and privacy

  • No invented numbers. Existing system prompt rule stays. Add: money figures must trace to a tool result or chunk from this turn; snapshot values are quoted with "as of <date>".
  • Stub disclosure. Everything is synthetic; demo UI shows a "sandbox data" badge, agent never says an offer is real.
  • Proportionate action. For next_best_moment personas (false alarms vs real churn risk) the guardrail is to prefer a human handoff over a discount. guardrails.escalateOn seeded with: cancellation_inquiry topic in 30d, port_out_inquiry=1, 3+ unresolved contacts, explicit request for a person.
  • Discount ceiling. maxDiscountPct low (e.g. 0 for monthly price; promo offers come only from eligible API results).
  • Don't upsell the wrong moment. Rule chunks: no upgrade pitch within 3 months of an upgrade with a balance owed; a financed trade-in charges the balance today, say so.
  • Minimum data. The prompt digest excludes anything not needed for the question; raw context is never shown to the customer wholesale.
  • Secrets. Sandbox base URL is not secret; any future real API key stays host-side per the existing platform-secrets rule.
