Agent PRD Set

Eight documents were written over several sessions. This page makes them one coherent plan: what each is for, where they disagreed, how each disagreement is resolved, and exactly what this pull request builds.

1. Purpose

The product is an AI sales/support agent per business, reachable by iMessage, SMS, WhatsApp and phone, grounded in the business's data, remembering each customer, and recorded completely in MongoDB. The documents describe it from different angles. Before building, I checked them against the code, against live measurements, and against each other. They disagreed in twelve places, and two of those would have caused bugs. Section 4 lists each and the fix.

5. Reconciled architecture

Roles

PieceResponsibilityNever does
IngestFast and durable: identify the person, store the message, acknowledge Photon, schedule the turnWaits for the model
SchedulerPer-conversation lane in Mongo: merge bursts, one turn at a time per person, many people in parallel up to caps, recover after a crashRuns two turns for one conversation at once
EngineBuilds context for exactly one person, runs the tool loop, applies guardrails, sends through the messenger, logs everythingLets the model choose a contact id, a destination number, or skip verification
SandboxIsolated per-business environment, pre-warmed on calls, runs sandboxed toolsHolds database, Photon, Daytona or model credentials

6. Contracts the implementation follows

Tools

name        snake_case, 1-64 chars: knowledge_search, memory_remember, verify_check_code ...
parameters  JSON Schema (validated before the tool runs; invalid arguments are an error result, not a crash)
risk        read | write_low | write_high           (write_high needs a code-level guard: consent, rate limit, approval)
requires    { verified?: boolean, channels?: [...] } (enforced by the executor, never by the prompt)
ctx         { orgId, contactId, conversationId, channel, party, customer, turnId } set by the engine from the thread or call
result      { ok, data?, error? }   data goes to the model; secrets (codes, links) are never in data
audit       every call writes tool_calls (args and result with secrets redacted); failures included

Turn

input   conversation + the batch of unanswered inbound messages + channel + mode ("text"|"voice")
loop    model call -> if tool_calls: execute each -> append results -> model call ...  (max 4 rounds, then a safe fallback)
checks  guardrails on final text; pre-send re-check (still agent mode? newer inbound arrived?)
output  { outcome: "reply"|"escalated"|"discarded"|"failed", text, rounds, toolCalls, usage, ms }  stored as agent_turns

Messenger

sendOutbound({ orgId, contactId, conversationId, purpose: "reply"|"otp"|"form_link"|"info", body, redact?, channels? })
  1. consent for the purpose   2. opt-out   3. rate limits   4. first READY channel   5. store (redacted if needed)   6. send with idempotency key
  destination always comes from the contact's handles, never from the caller of this function

Verification

send:  6 digits (crypto random) -> HMAC stored, 5 min expiry, 5 attempts, 30 s cooldown, 3/hour, 10/day per number
check: constant-time compare on the server; success sets contacts.verifiedPhone {number, at, method}; the model never sees the code

Data additions (additive; Atlas validators extended)

WhereWhat
conversations.lanedueAt, state, owner, leaseUntil, cursor
contacts.memory / consent / verifiedPhonesummary, openLoops; per-channel text consent with source; phone-possession proof
new verifications, opt_outs, agent_turns, notificationscodes (hashed), STOP list, one row per turn, owner notices

1Two messages arriving at once on different channels from a new number created two contacts (uniqueness was per channel)Split identity: memory and verification would not follow the person. Fixed with a database-level unique index across channels

  • A real iMessage through the new scheduler. The old path is verified live; the new one needs you to text the number. The runner can be switched back with ENGINE=legacy.

9. Needs your sign-off

  1. D-A1. Engine location. This PR runs the engine on the platform host, not inside the Daytona sandbox, which departs from your stated route (phone → ElevenLabs → agent on Daytona → back). Reasons: the sandbox correctly has no database or messaging credentials, so a sandbox-resident engine would call back to the host for context, memory, verification, forms and handoff, and every such call adds latency and complexity. The sandbox remains one per business, pre-warmed, and is where sandboxed tools run. If the Daytona-resident engine is a hard requirement, say so and I will plan it as the next PR, with the extra host calls costed against the latency budget.
  2. D-A2. Model credential. Engine on the host means the model key never enters a sandbox (the safer option from VOICE-LATENCY D1).
  3. D-A3. Account details only after verification. The T-Mobile stream's prompt builder currently includes them unverified. OK to require verification there too?
