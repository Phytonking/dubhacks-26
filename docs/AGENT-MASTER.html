Agent PRD Set

Eight documents were written over several sessions. This page makes them one coherent plan: what each is for, where they disagreed, how each disagreement is resolved, and exactly what this pull request builds.

1. Purpose

The product is an AI sales/support agent per business, reachable by iMessage, SMS, WhatsApp and phone, grounded in the business's data, remembering each customer, and recorded completely in MongoDB. The documents describe it from different angles. Before building, I checked them against the code, against live measurements, and against each other. They disagreed in twelve places, and two of those would have caused bugs. Section 4 lists each and the fix.

6. Contracts the implementation follows

Tools

name        snake_case, 1-64 chars: knowledge_search, memory_remember, verify_check_code ...
parameters  JSON Schema (validated before the tool runs; invalid arguments are an error result, not a crash)
risk        read | write_low | write_high           (write_high needs a code-level guard: consent, rate limit, approval)
requires    { verified?: boolean, channels?: [...] } (enforced by the executor, never by the prompt)
ctx         { orgId, contactId, conversationId, channel, party, customer, turnId } set by the engine from the thread or call
result      { ok, data?, error? }   data goes to the model; secrets (codes, links) are never in data
audit       every call writes tool_calls (args and result with secrets redacted); failures included

Turn

input   conversation + the batch of unanswered inbound messages + channel + mode ("text"|"voice")
loop    model call -> if tool_calls: execute each -> append results -> model call ...  (max 4 rounds, then a safe fallback)
checks  guardrails on final text; pre-send re-check (still agent mode? newer inbound arrived?)
output  { outcome: "reply"|"escalated"|"discarded"|"failed", text, rounds, toolCalls, usage, ms }  stored as agent_turns

Messenger

sendOutbound({ orgId, contactId, conversationId, purpose: "reply"|"otp"|"form_link"|"info", body, redact?, channels? })
  1. consent for the purpose   2. opt-out   3. rate limits   4. first READY channel   5. store (redacted if needed)   6. send with idempotency key
  destination always comes from the contact's handles, never from the caller of this function

Verification

send:  6 digits (crypto random) -> HMAC stored, 5 min expiry, 5 attempts, 30 s cooldown, 3/hour, 10/day per number
check: constant-time compare on the server; success sets contacts.verifiedPhone {number, at, method}; the model never sees the code

9b. Reaching people: calling and texting, and keeping secrets out of conversations

Requirement: when the agent on a call needs credentials or information, it asks over text, from a different number (and says which) or through WhatsApp; and a person who messages and wants to call is given the proper phone number.
PieceWhat it does
Real numbers per channelThe phone (voice) number, the WhatsApp number and each iMessage line are recorded as lines of the business (channel_lines). The live runner registers them from Photon. The iMessage line is a different number from the phone number; on the current plan it can only chat with people it was assigned to.
Always in the prompt"How customers reach this business": the phone number in written form and in spoken digit groups, and the WhatsApp number. So when someone on iMessage, WhatsApp or (later) email asks how to call, the agent answers with the phone number without any tool. If no phone number is configured it offers a person instead of guessing.
contact_options toolFor a caller who needs to give private details, get a code or a form: finds the iMessage line to text (reusing the caller's existing assignment, or assigning one on request) and the WhatsApp number, with written and spoken forms. Remembers that the customer is moving to text, so their first message there is finished without starting over.
Deterministic replyWhen nothing can text the caller yet, the tool supplies the exact reply ("please don't say them out loud. Please send a quick text on iMessage to six two eight, nine nine nine, zero zero zero one, which is a different number from the one you called, or send a message on WhatsApp to ...") and the engine uses it as is. verify_send_code, forms_send_secure_form and text_send_info do the same on "no channel". Real-model runs showed the model sometimes skims a tool result, so the numbers are not left to it.
Channel readinessiMessage is usable once the person has messaged the line; WhatsApp for 24 hours after their message (outside that, an approved template would be needed). Once they message, verify_send_code and forms_send_secure_form just work.
Assignment limitsAssigning an iMessage line uses one of the plan's assignments (25 on Free). The runner caps itself (default 20, IMESSAGE_ASSIGN_CAP) and is now off by default (AUTO_ASSIGN_IMESSAGE=1 turns it on); when refused or full, WhatsApp is still offered.

9c. T-Mobile data, learning about new customers, one-way text

Decisions (2026-10-18): only one iMessage test line is kept (no auto-assignment); WhatsApp and the phone number are the customer-facing channels; a caller may text the call number, which we read but cannot answer (no 10DLC campaign); no email.
PieceWhat it does
Real data in AtlasThe T-Mobile business holds 11 plans, 62 phones, 21 promotions, 31 add-ons, 5,042 household accounts, 54 knowledge rows and 50 demo customers (imported by web/scripts/seed-tmobile.mts; it is synthetic sandbox data). The live runner serves it with LIVE_ORG=T-Mobile, and the agent uses the T-Mobile prompt (agents.promptTemplate).
Read: tmo_catalogPublic, no verification: plans (exact monthly total for N lines, summed in code from marginal line prices and noting AutoPay), phones (price, trade-in estimate for a phone of a given age), promotions (value and conditions in words; it does not say a customer qualifies), add-ons (price, deductibles).
Read: tmo_contextUnchanged: one verified customer's own lines, devices, balances, bill, support.
Write: customer_profile_updateSaves what the person said: first name, carrier, plan, monthly bill, lines, phones, budget, needs, preferred contact. Later answers replace earlier ones, lists accumulate. Refuses secrets. An unknown number becomes a tracked prospect on its first saved fact; each save records its source (call or message).
Savvy, not creepyThe prompt gives the manner (why you ask, one question at a time, accept "no", reflect back, never ask for what you do not need, never reveal lookups) and the record shows "Not known yet" so the model asks the next useful thing only. Verified in the live run: one question per turn, did not re-ask what she had told it, accepted "I'd rather not say".
On a callThe live agent records as the caller speaks. After the call, the transcript is read once more and anything missed is added (fills gaps only, never overwrites), stored on the call (calls.extracted) and attached to the same contact, so the new caller becomes a customer record with plan and device. This needs the ElevenLabs post-call webhook; Photon's own call events carry no transcript.
Text-in, no replySMS runs listen-only until a campaign is approved: the text is stored, the model reads it and records facts, nothing is sent (not even STOP/HELP). The prompt tells the model its reply will not be delivered.
ConsoleThe contact page shows "What we know (they told us)".

Tests: 147 offline (new intake-test.ts: 14), live model 22 checks (11 new-caller scenarios included). Not verified: a real ElevenLabs call (so post-call extraction ran only on simulated webhooks), a real inbound SMS in listen-only mode, and a real WhatsApp reply from the new engine.

9e. Why customers were sent to a person, and the guard that stops it

Incident (2026-10-18): every call and text was answered with "let me connect you with someone from the team" and the agent did nothing. Cause: a heuristic I added ("the reply promised a person, so hand off") fired on a goodbye and locked the conversation to a person. Voice then returned a canned line in 30 ms for every later call. Both locks in the data were caused by the system, none by a customer.
Path that could send a customer to a person or a canned replyProblemNow

The single gate: src/handoff.ts (recordHandoff). Only customer_request and policy causes lock a chat; system never does. Watchdog: the live runner checks every minute, hands back any chat locked by a system fault, and alarms the team if more than 25% of the last hour's turns ended in an escalation, block or failure. Audit: scripts/handoff-audit.mts lists locked chats and handoff reasons by cause.

Regression tests: handoff-test.ts; in the conversation suite every scenario outside real escalations fails if the chat was locked or a handoff tool succeeded, and a new "M" group checks the agent acts on its own (texts details, sends a secure form, records a purchase, records a callback, remembers the customer).

9. Needs your sign-off

  1. D-A1. Engine location. This PR runs the engine on the platform host, not inside the Daytona sandbox, which departs from your stated route (phone → ElevenLabs → agent on Daytona → back). Reasons: the sandbox correctly has no database or messaging credentials, so a sandbox-resident engine would call back to the host for context, memory, verification, forms and handoff, and every such call adds latency and complexity. The sandbox remains one per business, pre-warmed, and is where sandboxed tools run. If the Daytona-resident engine is a hard requirement, say so and I will plan it as the next PR, with the extra host calls costed against the latency budget.
  2. D-A2. Model credential. Engine on the host means the model key never enters a sandbox (the safer option from VOICE-LATENCY D1).
  3. D-A3. Account details only after verification. The T-Mobile stream's prompt builder currently includes them unverified. OK to require verification there too?
