Agent Architecture: threads, memory, concurrency

How one agent per business serves many customers at the same time without mixing them up, dropping messages, or answering twice.

Review 2026-10-18: Amendments: the conversation summary lives on contacts.memory.summary, not conversations.summary (C8); tools are named in snake_case (C7); the engine library runs on the host in v1 (C1, decision D-A1). See AGENT-MASTER.html.
Status 2026-10-18: Gaps G1 to G9 (section 3) are fixed in branch agent/core-v1: ingest no longer waits for the model (30 messages stored and scheduled in about 50 ms), per-conversation lanes order messages and merge bursts, crashes are recovered by lease expiry, caps and single-flight wake bound the load, contact memory and summaries reach the model, and sends are idempotent. Each has a test (see AGENT-MASTER section 9a).

1. Short answers

Does the agent have threads?Yes, but the agent itself holds none. A thread is a conversation in Mongo (one per contact, spanning channels). The agent is stateless between turns: each turn is rebuilt from Mongo for exactly one thread.
Does it share one memory?Two tiers. Shared: the business's persona, rules and knowledge, identical for every customer. Private: each contact's history, summary and facts, visible only inside that contact's turns. One giant shared chat context would leak customers into each other and cost far more.
Many customers at once?Parallel across threads, strictly one-at-a-time within a thread. A per-thread "lane" in Mongo orders messages, merges bursts into one reply, survives crashes, and caps total load.
Can customers see each other's data?Not by construction: ids are set by our worker, never by the model, and a canary test enforces it (§13).
Bottom line. The pipeline you already have (provision sandbox → agent builds prompt → host calls the LLM → guardrails → send, all logged) is a good single-customer core and already stateless per turn, which is the right foundation. What's missing is the scheduling layer in front of it and the memory layer inside it. Both are small, and both fit in Mongo with no new infrastructure.
Update 2026-10-18: the statement below that the sandbox "cannot reach the internet" is no longer true. A probe today reached Modal, npm and other hosts from inside a sandbox (VOICE-LATENCY.html §3). The host-side model call is therefore a security choice (keep the model credential out of the sandbox), not a network necessity. Section 9 (harness) reasoning that depended on blocked egress should be re-read with that in mind.

3. Gaps found (what breaks with many customers)

These are from reading the code, not guesses. Each is a concrete failure under load.

#GapWhat happens
G1blocking Live socket processes events strictly one at a timePhotonEvents awaits the handler, and the handler awaits the entire agent turn, then saves the cursor. 20 customers texting together means the last one waits ~20 × 1.5 s = 30 s. One slow or hung turn freezes every business on that Photon project.
G2blocking Same customer, rapid messages: no orderingWebhook path runs every message's turn in parallel. "Do you have size 54?" then "and in blue?" start two turns that both read history before either reply is stored. Result: two replies, possibly contradictory, possibly out of order.
G3blocking A crash loses the replyThe message is stored (received) and acked, then the turn runs only in process memory. If the worker restarts or ensureOnline throws, nothing retries it. The customer is silently ignored.
G4gap Unbounded parallel loadWebhook path has no cap: a burst of 100 messages is 100 simultaneous Modal calls and 100 simultaneous wake attempts on a stopped sandbox (wake has no single-flight guard).
G5gap Contact memory never reaches the agentThe turn payload carries org, agent and knowledge only. contacts.facts, stage and notes are not sent and nothing writes facts. The agent knows the product but not the person.
G6gap History is a 6-message window, no summaryConversations last forever (one per contact). Message 40 forgets what message 3 established.
G7gap Stale repliesIf the customer sends another message while the LLM is generating, the finished reply answers an outdated state.
G8gap Whole knowledge base shipped each turnAll knowledge docs travel in every turn and are keyword-matched. Fine for a 10-line FAQ, wrong for a catalog.
G9Retry would double-sendclientMsgId is a fresh random UUID per attempt, so Photon's idempotency key cannot protect a re-run turn.

4. Design principles

  1. The agent is stateless between turns. Mongo is the memory. Sandbox disk and process state are disposable.
  2. A turn serves exactly one conversation. Nothing from another contact is ever loaded into it.
  3. Context = shared business layer + private contact layer. Different lifetimes, different owners (§5).
  4. Serial within a thread, parallel across threads. Order matters per customer; throughput matters across customers.
  5. Persist first, schedule second, act last. Acking Photon means "stored", not "answered". A stored-but-unanswered message must always be recoverable.
  6. At-least-once work, exactly-once effect. Turns may be retried; the send is idempotent by a deterministic key.
  7. Host orchestrates, sandbox executes tools. Keeps secrets and the model call outside the untrusted box (already true today).

5. Threads and memory

A thread is a conversation: one per contact, shared across iMessage, WhatsApp, SMS and voice. When a turn starts, the worker assembles that thread's context from five layers:

LayerShared or privateStored inWho writes it
L1 Business rulessharedorgs, agentsOwner in the console
L2 Knowledgesharedknowledge, knowledge_chunksOwner (upload) and ingest job
L3 Contact profileprivatecontacts (name, stage, score, facts[])Agent tools remember_fact, update_stage; owner edits
L4 Summaryprivateconversations.summary (new)Background summarizer
L5 Recent messagesprivatemessagesWorker (in and out)
Turn scratch (tool results)transientdiscarded after the turn; audited in tool_calls—

Isolation rules (enforced in code, not by prompting)

  • The worker stamps every turn with (orgId, conversationId, contactId). Tool implementations read ids from that envelope. The model never supplies an id, so it cannot ask for another contact.
  • No tool lists or searches contacts. The only cross-customer reads are owner-facing, in the console.
  • Learning across customers (e.g. "many ask about Brompton bikes") goes to an owner-reviewed insights queue. It is never injected automatically into another customer's context.
  • One conversation spans channels, so a contact who iMessages and then calls gets one continuous thread, but only their own.

6. Concurrency: many customers, one agent

Each conversation is a lane. Lanes run in parallel; messages inside a lane are handled in order, and bursts are merged. State lives on the conversation document, so it is durable and visible to every worker instance.

Illustrative timings. The first inbound message starts the sandbox wake immediately, so the 2-second merge window hides most of the 3-second cold start. Maya gets one answer to all three messages, not three.

Mechanism

conversations.lane = {
  dueAt:      Date | null,   // when the next turn may start (now + debounce, extended per new message, capped)
  state:      "idle" | "running",
  owner:      string | null, // worker instance id
  leaseUntil: Date | null,   // crash recovery: expired lease = reclaimable
  cursor:     ObjectId | null // last inbound message already answered
}

1. INBOUND (fast path, runs inside the Photon handler, ~10 ms)
   persist message (existing dedupe key) -> set lane.dueAt = min(now + 2s, firstUnansweredAt + 8s)
   -> ack Photon -> advance Photon cursor.        // no agent work happens here

2. DISPATCH (loop in the worker, every ~250 ms)
   claim = conversations.findOneAndUpdate(
     { "lane.dueAt": {$lte: now}, mode: "agent",
       $or: [{"lane.state":"idle"}, {"lane.leaseUntil": {$lt: now}}] },
     { $set: {"lane.state":"running", "lane.owner": me, "lane.leaseUntil": now+60s} })
   honour caps before claiming: global in-flight, per-org in-flight.

3. TURN: batch = inbound messages after lane.cursor; build context (§8); run (§7)

4. COMMIT: re-check mode and newer inbound (§7 step 8); send with a deterministic idempotency key;
   set lane.cursor = last batch message, state = idle; dueAt stays null unless new messages arrived.
ConcernHow it is handled
Messages from one customer, fastSame lane: debounced into one batch, answered once, in order.
Many customers at onceDifferent lanes run in parallel, up to global cap (start 8 turns) and per-business cap (start 3). Excess waits in dueAt order, oldest first, round-robin across businesses so one busy business cannot starve others.
Worker crash mid-turnLease expires after 60 s; another dispatcher reclaims the lane and re-runs from cursor. Reply send uses key turn:{conversationId}:{lastInboundId}, so a retry cannot double-send.
Worker restartNothing is in memory that matters: any conversation with dueAt set or an expired lease is picked up on boot. This closes G3.
Sandbox asleep, 50 lanes duewake(orgId) becomes single-flight: one in-process promise per business (and a Mongo lease if we run several workers). All 50 lanes await the same wake.
Customer writes while the model is thinkingStep 8 of the turn compares newest inbound id to the batch. If newer messages exist and no side-effecting tool ran, discard the draft and re-run with the larger batch (max 2 reruns). Otherwise send, then the lane re-fires for the new messages.
Owner takes over mid-turnMode is re-read just before sending; if now human, the draft is dropped and logged.
Photon socket head-of-line blocking (G1)The handler now only persists and sets dueAt (milliseconds), so the strictly-serial socket consumer is never blocked by an LLM call.
Agent process in the sandboxStateless HTTP handlers: concurrent turns for different lanes are just concurrent requests. LLM time is host-side (not sandbox CPU). Heavy tools later get a per-sandbox concurrency cap.

7. Turn lifecycle

  1. Persist and schedule (§6 step 1). Photon is acked.
  2. Claim the lane once dueAt passes and caps allow.
  3. Ensure sandbox online (single-flight wake).
  4. Build context (§8) for this conversation only.
  5. Tool loop, host-orchestrated: sandbox /turn returns the prompt; host calls the LLM; if the completion asks for a tool, host posts it to a new sandbox /tool endpoint, appends the result, calls the LLM again. Maximum 4 rounds, then a safe fallback reply. This is a small extension of today's two-phase /turn → LLM → /finalize.
  6. Tools available (v1): knowledge_search (exists), remember_fact, update_stage, escalate_to_human. Later: inventory lookup, booking, payments. Each runs with ids from the envelope and is logged to tool_calls.
  7. Guardrails on the final text, outside the model (exists: discount cap). Blocked drafts are stored as blocked, never sent.
  8. Pre-send re-check: conversation still agent mode? newer inbound than the batch? (rules in §6).
  9. Send and record: existing queued → sending → sent path, with the deterministic idempotency key; advance lane.cursor; write agent_turns audit row and usage.

8. Context assembly and summaries

Summarizer

  • Runs in the background after a turn when unsummarized messages exceed the window (e.g. > 20 or > 2k tokens). Cheap model, low priority, same caps.
  • Writes conversations.summary = {text, throughMessageId, updatedAt}. Idempotent: it only folds messages up to throughMessageId.
  • Also proposes facts with sourceMessageId pointers; the owner can correct or delete any fact in the console.
  • Summaries are plain text and are regenerable from messages, so a bad summary is never fatal.

9. Harness decision, updated

The earlier PRDs leaned toward Hermes. What got built differs, and the multi-customer requirement adds a new constraint, so I'm revising that lean.

FactConsequence
Sandbox cannot reach the internet on the current Daytona tier, so the model call is made by the host.Hermes, which runs the whole loop inside its box, cannot run there as-is. A host-driven loop with sandbox-executed tools matches reality (and matches how fx is designed).
Hermes advertises self-improving, agent-wide memory (cross-session recall, user modeling) from its public docs.For one agent serving many customers, memory that accumulates across sessions is a leak path unless disabled. Default-on features are a liability here. VERIFY whether Hermes can be run with those turned off.
Our memory must live in Mongo and be scoped per contact.Any harness we adopt must be used as a pure turn function: context in, reply plus tool calls out.
Recommendation: keep the thin custom loop now (it already works: 1.2 s round trips). Add the tool loop and memory from §5–§8 ourselves; it's a few hundred lines. If we want a library for the host-side tool loop, use the AI SDK agent loop or fx in a stateless mode. Re-evaluate Hermes only for a different product (an owner-facing assistant), where cross-session memory is a feature. I'd keep the AgentRuntime interface so this stays swappable.

12. Worked example

Sunrise Bike Shop's sandbox is asleep. At 10:00:00 three things happen:

TimeEventSystem response
0.0 sMaya: "Hi, looking for a commuter bike"Stored, lane dueAt=+2 s, wake starts (single-flight).
1.5 sMaya: "under $1500"Stored, dueAt pushed to +2 s again.
2.0 sDevon (owner has taken over): "can I get a tune-up Thursday?"Stored, mode is human: no lane, owner notified.
3.0 sMaya: "8 mile commute"Stored, dueAt → 5.0 s. Sandbox is awake by now.
4.0 sPriya: "what are your hours on Sunday?"Stored, own lane, dueAt → 6.0 s.
5.0 sMaya's lane firesContext = business rules + knowledge hits for "commuter bike" + Maya's profile + her 3 messages. One reply to all three. Facts saved: budget $1,500, 8-mile commute.
6.0 sPriya's lane fires, overlapping Maya's turnContext contains nothing about Maya. Replies "closed Sundays".
7.0 sMaya sends "and e-bikes?" while her second turn is generatingPre-send check sees a newer message, no side-effecting tool ran → draft discarded, re-run with the new message, one reply.

15. Open questions

  • Debounce window. 2 s with an 8 s cap is a guess; iMessage users send bursts but expect quick replies. Tune with real traffic. Voice bypasses the debounce entirely.
  • Group chats. One conversation per space with per-participant attribution, or one per participant? Affects the schema and who the agent replies to. Default: group chats off in MVP.
  • Several worker instances. Mongo leases already allow it; decide whether MVP runs one instance (simpler) or two (no downtime on deploy).
  • Modal limits. Unknown concurrency and rate limits; the global cap should be set from a load test, not a guess.
  • Summarizer model and fact extraction policy. Which model, and may it write facts without owner review?
  • Caps per plan. Should maxConcurrentTurns be a pricing lever?
  • Hermes memory switches. Can its cross-session memory be fully disabled? Only matters if we revisit it.
