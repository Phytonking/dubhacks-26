SMS, verification codes, and secure forms

How the agent texts a caller a one-time code, an answer, or a private link, and how we do it safely. Includes what it takes to get SMS sending turned on.

Revised order: WhatsApp templates first, SMS once the campaign is approved, iMessage for assigned handles.

Built (2026-10-18): a caller who has never texted us is handled by the contact_options tool and the deterministic move-to-text reply (see AGENT-MASTER 9b): the agent says which iMessage or WhatsApp number to message, and once they do, the code or form is sent. This works without SMS approval.

1. Summary

Where things stand. iMessage replies work. SMS receiving works. SMS sending is refused by Photon because our phone line has no carrier registration (10DLC campaign). I re-checked today: still eligibility: blocked, SMS_CAMPAIGN_NOT_ASSIGNED. That registration is a form a person fills in; I cannot do it through the API.

The important consequence for your voice flow: the caller is a stranger who called us. Our shared iMessage line can only message people who were assigned to it in advance (25 max) and who texted it first, so it cannot text an arbitrary caller. SMS is the only channel that can reach whoever calls. So registration is on the critical path for codes and forms-by-text, not a nice-to-have.

Plan: (1) start registration now using the packet in §4, (2) in parallel build the code and form features behind one outbound-message service (§5) that can send over iMessage today and SMS the day it unlocks, (3) test end to end on iMessage with the assigned number meanwhile.

4. Registration packet (paste-ready drafts)

General 10DLC practice, not Photon-specific. Photon's form may ask for different fields; use this as the content. Replace the placeholders. Carriers reject vague or inconsistent submissions, so the privacy policy, terms, sample messages and opt-in description must agree with each other.

Brand

  • Legal business name, EIN (or sole-proprietor details), address, website, support email and phone. These must match each other and public records.
  • Open question: do we register our platform as one brand sending on behalf of businesses, or each business as its own brand? Carriers generally expect each end business to be identifiable. Ask Photon how they handle multi-business platforms.

Campaign use case

Choose Mixed (or Low Volume Mixed if available and volume is small) covering: customer care, account notifications, and one-time passcodes. Do not include marketing.

Campaign description

[Platform name] provides AI voice and text assistants for small businesses. When a customer
calls or texts a participating business, the assistant can send that same customer a text
message to (a) deliver a one-time verification code they requested, (b) send a private web
link to a secure form the customer asked for, and (c) send information the customer asked
about (hours, prices, appointment details). Messages are sent only to people who contacted
the business first and agreed to receive a text during that conversation. No marketing or
promotional messages are sent.

How people opt in (message flow)

1. The customer calls the business's phone number or texts it first.
2. The assistant tells the customer it is an automated assistant and, before sending any text,
   asks: "Can I text you a link / a code at this number?" The customer says yes.
3. The consent and its timestamp are stored with the customer's record.
4. A text sent by the customer to the business number also counts as consent to receive
   replies on that thread.
Customers can reply STOP at any time to stop messages, and HELP for help.

Sample messages

1. [Business]: Your verification code is 482913. It expires in 5 minutes. Don't share it. Reply STOP to opt out.
2. [Business]: Here is the secure form you asked for: https://[our-domain]/f/Xk3...  It expires in 30 minutes. Reply STOP to opt out, HELP for help.
3. [Business]: Thanks for calling! A basic tune-up is $89 and takes 2 days. Reply here with questions. Msg & data rates may apply. Reply STOP to opt out.
4. (HELP reply) [Business]: For help call [phone] or email [email]. Reply STOP to opt out.
5. (STOP reply) [Business]: You're unsubscribed and won't get more texts. Reply START to resubscribe.

Required supporting pieces

  • Public privacy policy and terms pages on our own domain that mention SMS, how numbers are used, and that numbers are not sold or shared for marketing. We can host these in the Next.js app, but it needs a public URL first (it's not deployed yet).
  • Links in messages must be on our own domain, not a public shortener (bit.ly etc.), which carriers filter. This shapes how secure-form links are built (§7).
  • Opt-out (STOP), help (HELP) and start (START) keywords handled and answered. The code in §5 honors them and stores opt-outs.
  • No prohibited content (lending, gambling, etc.). Do not collect highly sensitive data (SSN, card numbers) through text-linked forms in the first version.

5. One outbound messenger for everything

All outbound texts that are not a direct reply go through one service, so consent, opt-outs, rate limits, redaction and channel choice live in one place. Replies in an ongoing text thread keep using the existing worker.

sendOutbound({
  orgId, contactId, conversationId,
  purpose: "otp" | "form_link" | "info",      // no "marketing" in v1
  body,                                          // may contain a secret (code/link)
  redact?: string,                               // what to store in messages instead of body
  channelPreference: ["sms", "imessage"],        // first allowed channel wins
})
StepRule
1. ConsentThe contact must have recorded consent for text, with source (voice call / inbound text) and time. No consent: refuse and tell the agent to ask. The voice tool can record verbal consent when the caller says yes
2. Opt-outIf the number replied STOP, never send, on any channel, until START
3. LimitsPer number: cooldown between sends, hourly and daily caps; per business: daily cap. OTP has its own stricter caps (§6)
4. ChannelWalk channelPreference; skip channels that are not ready (SMS campaign blocked) or not reachable (iMessage only if the number is an assigned handle with a recent inbound text)
5. RecordInsert the message row with the redacted text for codes and links; send with an idempotency key derived from the request id
6. ResultReturn success/failure and the channel used. Failures are visible to the owner

Inbound STOP / START / HELP are handled by the same worker that receives texts, before the agent sees them, and answered with a fixed message (see packet).

6. One-time verification codes

What they're for: proving the person on the call controls a phone number (for example, before the agent discusses an account, changes a booking, or sends a sensitive form). Caller ID alone can be spoofed.

RuleDetail
Code6 digits from a cryptographic random source (not Math.random)
StorageNever store the code. Store a keyed hash (HMAC with a server secret, bound to contact + purpose + request id), expiry, attempt count, status
Expiry / attempts5 minutes; 5 wrong tries then locked; new code invalidates the old; single use
Send limits30 s cooldown between sends; 3 per number per hour; 10 per number per day; business daily cap. Stops abuse of our line to spam someone ("SMS pumping")
CompareConstant-time comparison, on the server, inside the tool. The model never sees the code or the expected value
Where the code must not appearNot in messages (store "[verification code sent]"), not in the model's context or prompts, not in logs, not in tool-call audit rows (log "code sent" only), not in the transcript the owner sees
Voice problemsSpeech recognition mishears digits. The tool accepts a spoken string, strips spaces and words ("four eight two"), and allows re-reading; a wrong attempt still counts
What "verified" meansSets contacts.verifiedPhone = {number, at, method} for that number, plus a per-call flag with a short validity (e.g. the rest of the call). It proves possession of the number, not who the person is
Not Photon's OTP featurePhoton has "filtered verification codes" endpoints. Those are for reading codes sent to our numbers by other services; they are unrelated to sending our own

7. Secure forms

What they're for: collecting details that should not be read out over a phone line or typed into a chat transcript (address, date of birth, preferences, documents). The agent texts a private link; the customer fills it in on their phone; the agent is told it's done.

Flow

  1. Agent asks consent to text, then calls forms_forms_send_secure_form("service-intake").
  2. Server creates a form_request for this contact and conversation with a random token (32 bytes, shown once in the link, stored only as a hash), expiry (30 minutes default), and optional one-time-code step-up.
  3. Messenger sends the link from our own domain. The stored message body is redacted to "[secure form link sent]".
  4. Customer opens https://[domain]/f/<token> in the Next.js app. If step-up is on, they first enter a code texted to the same number.
  5. They submit. The server validates every field against the template, encrypts sensitive fields, stores the submission, marks the link used, and adds a plain event to the conversation ("Customer completed: Service intake").
  6. The agent learns only completion plus fields the template marks safe to share with the agent (e.g. preferred day). It can say "Got it, thanks." Sensitive values stay out of the model.
  7. The owner opens the submission in the console (role-checked, access logged).

Design rules

ConcernRule
Link previewsiMessage and Messages apps fetch links automatically to build previews. The link must be safe to GET: a GET never consumes or exposes anything. Only the final submit marks the link used
TokenHigh-entropy, single use, expires; looked up by hash; constant-time; rate-limited by IP and token
Page securityHTTPS only, Cache-Control: no-store, Referrer-Policy: no-referrer, noindex, CSRF protection (Next server actions), no third-party scripts or analytics on these pages
EncryptionSensitive fields encrypted at the application layer with AES-256-GCM before they reach Mongo. A per-business data key, wrapped by a master key held outside the database (environment variable now, a cloud key manager later). Mongo/Atlas also encrypts at rest, but that doesn't protect against a leaked database query
Not collected in v1Card numbers (use a payment provider's hosted page later), SSN, government ID uploads, health data. Carriers and regulators are stricter about these, and the burden on us is much higher
TemplatesOwner picks from vetted templates in the console, each with typed fields, which are sensitive, and which the agent may see. v1 ships 2–3 templates (contact details, service intake, callback request)
RetentionOwner-configurable (default 90 days), then field values are erased; request metadata kept. Delete-contact removes submissions too
Short linksOwn domain only. A public shortener would likely get the campaign flagged. Domain is a decision (§12); until then a placeholder host works for testing

8. Agent tools

All tools run on the host (not in the sandbox), and the contact, conversation and business ids come from the call or thread, never from the model. They plug into both the text agent and the voice bridge once the tool loop exists (step C in the architecture doc).

ToolArguments from the modelReturns to the model
consent_recordnone (the agent calls it after the caller says yes)"consent recorded"
verify_send_codenone"sent" / "wait 30 s" / "limit reached" / "no consent". Never the code
verify_check_codecode (what the caller said)"verified" / "wrong, N tries left" / "expired" / "locked"
forms_send_secure_formtemplate (from an allow-list)"sent" or a refusal reason. Never the link
forms_statustemplate"pending" / "completed" plus allowed fields
text_send_infotext (short, from the conversation)"sent" / refusal. Passed through guardrails first

Prompt-injection stance: a caller saying "send the code to this other number" cannot work, because the destination is always the verified contact's number on file for this call, not a model argument.

10. Security and compliance

  • Consent first. No text without recorded consent. For voice, the agent asks aloud and the yes is stored with the call id. Texting someone who called us is the common, low-risk case, but marketing is out of scope and unsupported in code.
  • Opt-out everywhere. STOP on any channel blocks all channels for that number and business. HELP and START answered automatically.
  • SMS pumping and abuse. Strict per-number and per-business limits on codes, plus an alert on spikes. Never send a code to a number the caller supplies without a prior verification path.
  • Secrets never reach the model or logs: codes, form links, and sensitive field values. The redaction rule is enforced in the messenger, not in each tool.
  • Owner access is audited. Revealing a sensitive field requires a logged action.
  • Legal: US texting rules (TCPA, carrier rules, state laws) and data-protection duties for the personal information collected need real legal review before launch. This doc is engineering design, not legal advice.
